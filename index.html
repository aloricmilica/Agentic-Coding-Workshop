Foundations

Four ideas worth five minutes before you touch the agent. Everything else today is these ideas applied.

1 · Think like an LLM

Context beats prompting

A model predicts the next token using only what's in its context window — training data, plus whatever you've fed it this conversation. It doesn't know your codebase, your BC version, or your customer's brief unless you put it there.

That's why "write a better prompt" only goes so far: a beautifully worded request over missing context still produces a confident guess. The lever that actually moves output quality is what you put in front of the model — the brief, the tech design, the real BC source — not the cleverness of the ask.

2 · From LLM to agent

Context, model, harness

An agent is an LLM wired into a loop: it reads context, decides on a tool call, gets a result back, and reads that into its next turn — repeatedly, until it decides it's done.

Three things shape what it can do: the context you give it (specs, source code, MCP servers), the model itself (Opus reasons more carefully, Sonnet moves faster), and the harness — the tools it's actually allowed to call. It has no memory between sessions; the harness resends context every single turn. You're not pairing with a colleague who remembers yesterday — you're the architect deciding what walks into the room each time.

3 · Vibe → agentic coding

Plan first, then direct

Vibe coding is the loop most people start with: describe what you want in a message, the agent writes something, you look at it, you ask for changes. It doesn't scale — as the conversation lengthens, the agent loses track of earlier decisions because of context limits, and you end up re-explaining things you already said.

Agentic coding front-loads the planning instead: written specs that persist independent of chat history, so the agent works in a bounded scope — one feature at a time — and can verify its own work through testing rather than relying on you to catch every regression by eye.

4 · Spec-driven development

Write it down first

The discipline that keeps agentic projects coherent. A constitution — brief, tech design, roadmap, coding rules — gets agreed once, before any feature code, so every later prompt has something authoritative to read instead of re-litigating decisions each session.

Then every feature runs the same loop: spec, implement, test, document, finalise. The specs aren't paperwork for its own sake — they're what lets you close a chat, open a fresh one tomorrow, and have the agent pick up exactly where you left off.

One thing before we start

Everything below is a workflow, not a tool. Swap in whichever agent you use — the discipline is what compounds: spec before code, review before merge, tests before you call it done.

Resist the urge Don't open the agent and ask it to "build the rental extension." Every section below breaks that instinct into a smaller, checkable step — that's the actual skill being taught today, not the AL code it produces.

The brief

Our customer rents out equipment — power tools, AV gear, event kit — to business customers by the day. Three capabilities, in build order:

Row 1

Equipment register

What we own, its daily rate, and whether it's available, out on rent, or in maintenance.

Row 2

Rental agreements

A customer rents one or more items for a date range. Catch double-bookings; record checkout and checkin.

Row 3

Pricing & posting

Charge is days × daily rate. Closing an agreement posts it as a ledger transaction.

Do this now Create specs/brief.md in your repo and paste the three rows above into it, in your own words if you like. This file is the anchor document — every prompt from here on tells the agent to read it, so it needs to exist before Constitution starts.

Constitution

Before any feature code, agree the shape of the whole extension with your agent, and write down how you expect AL code to look. Three documents plus one gut-check, about twenty-five minutes.

A
Tech design

specs/tech-design.md

Model: Claude Opus 5 · BC source + Microsoft Learn MCP active

prompt

Read specs/brief.md carefully. You have access to the full Business Central source code in external/BCApps and to Microsoft Learn via MCP. Use both. Produce specs/tech-design.md with the following structure: for each requirement in the brief, write a section with: 1. What standard Business Central already provides to cover this requirement — cite specific BC source files or Microsoft Learn URLs as evidence. 2. What gaps remain that standard BC cannot cover without custom code. 3. A brief implementation decision: how we will implement this feature, favouring standard BC features, configuration, and extension points over custom development. Do not write AL code. Describe the approach in plain language. Ground rules: - Exhaust standard BC options before proposing custom tables, documents, or posting logic. - Where standard BC covers a requirement, cite evidence — don't propose a custom alternative anyway. - Keep custom code thin; prefer extending existing objects over creating new ones. - Don't guess — say what you researched if you're not sure.

B
Stress-test

A second opinion on tech-design.md → iterate until no new issues surface

Model: Claude Opus 5 · BC Code Intelligence MCP active

The agent that wrote the design is anchored to its own reasoning. A second, independent pass — reading only the brief and the design, not the conversation that produced it — catches unaddressed requirements, custom work where standard BC already does the job, and claims about BC behaviour that were never actually verified.

  1. Install BC Code Intelligence MCP from github.com/JeremyVyska/bc-code-intelligence-mcp — follow the install instructions in the repo README
  2. Choose your approach: continue the current chat (recommended), fork it, or open a new one
  3. Select Opus 5 and activate the BC Code Intelligence MCP
  4. Paste the critique prompt below
  5. Take the critique seriously — revise specs/tech-design.md based on what it finds. If Alex Architect flags something, ask Opus to revise specs/tech-design.md accordingly. Repeat until no new issues surface.
prompt

Take a fresh look at the suggested @specs/tech-design.md using subagent. Use the Alex Architect persona from BC Code Intelligence (bc-knowledge mcp). Read specs/brief.md and specs/tech-design.md. Your job is to critique the tech design — not to be polite about it. Look for: 1. Requirements from the brief that are not addressed in the design. 2. Proposals for custom development where standard BC functionality already exists. 3. Over-engineered solutions where a simpler standard approach would work. 4. Any design decision that lacks justification or evidence from the BC source or Microsoft documentation. 5. Hallucinations — for every claim that a standard BC feature covers a requirement, verify it against the actual BC source in external/BCApps. If the feature does not exist, does not work the way the design describes, or is missing key capabilities needed to fulfil the requirement, call it out explicitly. For each issue you find, state: what the problem is, what a better approach would be, and where in the BC source or Microsoft Learn you found evidence for your recommendation. Do not summarise what the design does well. Focus only on what should change.

D
Coding guidelines

AGENTS.md, via a reusable skill

Without shared rules, quality drifts — every new agent session is a fresh start. AGENTS.md is the contract: "this is how we write AL here, always." It's small enough to matter every time and boring enough that no one wants to write it by hand — which is exactly what makes it worth automating once.

1. Create the folders

In your workspace, create two empty folders: .copilot/rules/ and .copilot/skills/.

2. Create the skill file

Create .copilot/skills/setup-al-agentic-rules.md and paste in this definition:

file · .copilot/skills/setup-al-agentic-rules.md

--- name: setup-al-agentic-rules description: Bootstrap an AL project with the official Microsoft AL agentic rules from the alguidelines GitHub repo. Downloads all rule files to .copilot/rules/, adds .copilot/ to the workspace file, and writes or updates AGENTS.md with a standard three-section scaffold. Use when starting a new AL project, onboarding a new developer, or refreshing stale rule files. disable-model-invocation: true --- # Setup AL Agentic Rules Fetches the official Microsoft AL coding rules from GitHub and wires them into the project so every future agent session follows them automatically. ## Step 1 — Discover files in the GitHub folder Call the GitHub Contents API to get the current file list (never hard-code filenames): GET https://api.github.com/repos/microsoft/alguidelines/contents/content/docs/agentic-coding/vibe-coding-rules Parse the JSON response and collect every entry where "type": "file". Extract the name and download_url of each file. ## Step 2 — Download each file directly into .copilot/rules/ Ensure the .copilot/rules/ directory exists, then download every file from its download_url into .copilot/rules/<filename>. Do NOT use WebFetch and then Write — download straight to disk. On Windows (PowerShell): ```powershell New-Item -ItemType Directory -Force -Path ".copilot/rules" | Out-Null Invoke-WebRequest -Uri "<download_url>" -OutFile ".copilot/rules/<filename>" ``` Run all downloads in one shell call by chaining them with ; so every file is saved in a single round-trip. ## Step 3 — Add .copilot/ to the workspace file The .code-workspace file sits at the repo root — the same directory that contains app/, specs/, test/, and AGENTS.md. Do not assume the current working directory is the repo root when inside a workspace. Locate the workspace file explicitly: ```powershell $repoRoot = (Get-Item (Resolve-Path "specs/brief.md")).Directory.FullName $workspaceFile = Get-ChildItem -Path $repoRoot -Filter "*.code-workspace" | Select-Object -First 1 -ExpandProperty FullName ``` Then read the JSON, add { "path": ".copilot" } to the folders array if not already present, and write it back. The path .copilot is relative to the workspace file location (i.e. the repo root), so no absolute path is needed. ## Step 4 — Write AGENTS.md Write (or overwrite) AGENTS.md in the repo root with exactly this structure and wording: # <Project Name> — Project Rules ## What this project is <One sentence describing the BC extension and its business domain.> Read `specs/brief.md` for the full customer brief. ## SDD process This project uses Spec-Driven Development. Before implementing anything: 1. Read `specs/tech-design.md` and `specs/roadmap.md` 2. Every feature lives on branch `spec/YYYY-MM-DD-feature-name` 3. Create `specs/YYYY-MM-DD-feature-name/requirements.md` + `plan.md` + `acceptance.md` before writing any code 4. Loop: Spec → Implement → Test → Docs → Merge ## AL coding standards See `.copilot/rules/` for detailed rules. --- Fill in the project name and the one-sentence description from specs/brief.md. Do not add extra sections. Do not expand the SDD process list. Write it exactly as shown. ## Verification After completing all steps, confirm: - .copilot/rules/ contains all files from the GitHub folder - .code-workspace has { "path": ".copilot" } in folders - AGENTS.md exists at the repo root with all three sections ## Notes - Always fetch from GitHub — never generate or paraphrase rule content. - AGENTS.md should be kept short; detailed rules live in .copilot/rules/.

5
Package it

Turn what you learned into a skill

When you close this chat and open a new one for the next feature, the agent starts fresh. Everything it learned — how you structured the docs, how to review them — is gone. Skills fix this: instead of re-explaining the same things in every chat, you package the learning once and invoke it by name.

prompt

/create-skill Based on what we produced in this feature — the user-guide.md structure, the review process, and the corrections made — create a skill file at .copilot/skills/generate-docs.md that automates the same documentation workflow for the next feature.

The agent produces a skill that carries the workflow — and the lessons — into every future feature session automatically.
